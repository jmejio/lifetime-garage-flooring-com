# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Marketing site for Lifetime Garage Flooring (a Technifloors brand), a residential garage floor coating contractor headquartered in Lutz, FL, serving the greater Tampa Bay area. Static HTML/CSS/JS, no framework. Pages are regenerated from local Jinja2 templates by a small Python build step before committing (see Commands/Architecture below); GitHub Pages still serves the committed output as-is, with no server-side build.

For step-by-step content-editing procedures (create/update/delete a page, image conventions), see [README.md](README.md) — this file covers architecture and commands, README.md covers the task recipes built on top of it.

## Hosting

**This repo is hosted on GitHub Pages, serving directly from the `main` branch.** There is no staging environment and no CI/build pipeline — a push (or a merge) to `main` is a production deploy of the live public site, typically live within a minute or two. Treat commits to `main` accordingly:

- Don't commit anything you wouldn't want live immediately.
- `CNAME` (containing `www.lifetimegarageflooring.com`) is what maps the custom domain to GitHub Pages — don't remove, rename, or edit it, or the domain mapping breaks.
- `.nojekyll` (empty file at the repo root) tells GitHub Pages to skip Jekyll and serve the repo as plain static files — don't remove it. Without it, GitHub Pages runs every push through Jekyll, which converts markdown files (including this one) into themed HTML pages and fails the entire deploy if any file contains text Jekyll's Liquid templating misreads as its own syntax (this happened in practice: prose describing Jinja2's `{% block %}` tag in this file's Architecture section crashed the Jekyll build with "Unknown tag 'block'"). Keep it in the repo permanently, and be aware that `{{ }}`/`{% %}` in any committed file's prose — not just code — is a landmine unless `.nojekyll` is present.
- There's no `.github/workflows/` — Pages builds straight from the branch, so nothing in Actions needs to pass before it goes live.
- A local build step (`python build/build.py`) regenerates the static `*.html` files, `sitemap.xml`, and `robots.txt` from Jinja2 templates under `build/templates/` and `build/pages/` before you commit. This runs on your machine (or the agent's) only — GitHub never runs it, and Jinja2 is never shipped to the browser. The committed `*.html` files are still plain static output, and the "no CI/build pipeline" guarantee above is unchanged: nothing runs at deploy time, only ahead of a commit.

## Commands

There is no build/lint/test *pipeline*; there is one local Python dependency (Jinja2) used only by the page build step below.

- **Local preview**: serve the repo root with any static file server, e.g. `python -m http.server 8000`, then open `http://localhost:8000/index.html`. Opening the HTML files directly (`file://`) also works since there are no server-side dependencies. Editing a file under `build/` has no effect on what's served until you rebuild (below) — `python build/watch.py` does that automatically on every save; see README.md.
- **One-time setup**: `pip install -r build/requirements.txt` (installs Jinja2 into your system Python — no virtualenv needed for this single-dependency tool).
- **Build pages**: `python build/build.py` — regenerates all committed `*.html` files, `sitemap.xml`, and `robots.txt` from `build/templates/` + `build/pages/`. Run after editing anything under `build/`, then commit both the source changes and the regenerated output together.
- **Verify generated output is in sync**: `python build/build.py --check` — rebuilds in memory and diffs against the committed output; exits non-zero with a diff if anything is stale or was hand-edited. Run before committing any change touching `build/` or a root `*.html` file.
- **Deployment**: none needed — see Hosting above. Pushing to `main` is the deploy.

## Architecture

- The site started as two flat pages and has grown into a nested, metadata-driven structure that scales to new services/locations/resources/projects without touching index pages by hand. Pages are generated from local Jinja2 templates, not hand-duplicated. Source of truth lives under `build/`:
  - `build/templates/base.jinja` — the shared layout: head boilerplate, per-page `{{ title }}`/`{{ description }}`/`{{ canonical_url }}`/`{{ og_image }}` variables, the sitewide `_jsonld.jinja` include, a `{% block extra_schema %}{% endblock %}` for page-type-specific structured data (`Service`, `LocalBusiness`, `Article`, layered on top of the sitewide business schema, never replacing it), and a `{% block content %}` each page overrides.
  - `build/templates/_header.jinja` / `_footer.jinja` — shared header/footer partials, included via `{% include %}`. The header has one variable, `{{ logo_href }}` (`#top` on the home page — scrolls to the top of the current page — or `/index.html#top` everywhere else — navigates to the home page), plus Services and Locations dropdowns and direct Projects/Resources links — all generated by looping the `pages` lookup dict filtered by `page_type`, so no page is hardcoded into nav markup. The footer mirrors this with matching Services/Locations/More link columns alongside its static Get In Touch / Follow Us columns.
  - `build/templates/_breadcrumbs.jinja` — renders the visible breadcrumb trail and matching `BreadcrumbList` JSON-LD from a page's `breadcrumbs` metadata, or an auto-derived trail from `canonical_path` segments when `breadcrumbs` is `null`.
  - `build/templates/_components.jinja` — a small library of reusable content-section macros that every service/location/project/resource page imports and composes its body from, instead of hand-rolling markup: `benefits_grid(items)`, `process_steps(steps)`, `faq_accordion(qa_list)` (emits `FAQPage` JSON-LD only for real Q&A content, never for empty/placeholder input), `testimonial_quote(text, author)`, `cta_band(text, href)`, `related_links(title, items)`, `contact_form()` (the "Request a Free Quote" form markup — see `contact-form.js` below for its behavior half). Most, but not all, pages call `contact_form()`; the `/locations/`, `/resources/`, and `/projects/` index pages deliberately don't.
  - `build/templates/_jsonld.jinja` — the sitewide `HomeAndConstructionBusiness` JSON-LD block, included on every page. Its `image`/`url` fields are templated from `SITE_BASE_URL`; only `sameAs` (the LinkedIn company URL, unrelated to the site's own domain) stays hardcoded. Unchanged by the `extra_schema` block above — the two layer together.
  - `build/pages/<slug>.json` — per-page metadata: `title`, `description`, `canonical_path`, `og_image`, `is_home`, `sitemap_priority`, `sitemap_changefreq`, `page_type` (`home` / `service` / `location` / `resource` / `project` / `project-index` / `static`), `primary_keyword` (a reasoned SEO target, not measured search-volume data), `secondary_keywords` (list), `schema_type` (the `extra_schema` JSON-LD `@type`, or `null` when a page adds no extra schema), `breadcrumbs` (explicit `[{"label", "path"}, ...]`, or `null` to auto-derive from `canonical_path` segments), `related_services` (slug list — resolved via `build.py`'s `resolve_related()` into the page's rendered "related services" section, so this field is the live source of that content, not descriptive-only metadata; an unresolvable slug fails the build)/`related_locations`/`related_projects`/`related_articles` (slug lists, same `resolve_related()` treatment; `related_projects` and `related_articles` are currently populated on service/location pages only), `noindex` (bool, default `false` — when `true`, emits a `<meta name="robots" content="noindex, follow">` tag and excludes the page from `sitemap.xml`; `robots.txt` is deliberately unaffected, since a `Disallow` would stop crawlers from ever reading the page's `noindex` tag), and an optional `nav_label` (short nav/footer display text; falls back to the title's pre-`|` segment). Project pages (`page_type: "project"`) additionally carry `location`, `service`, `square_footage`, `scope_summary`.
  - `build/pages/<slug>.jinja` — the actual Jinja2 template for that page (`{% extends "base.jinja" %}` + a `content` block, typically `{% import "_components.jinja" as components %}` to compose its sections). Source files use a `.jinja` extension specifically so they never share a name with the generated output file, and source filenames stay flat (e.g. `services-epoxy-flooring.json`) even when the rendered page nests into subdirectories.
  - `build/build.py` — reads the above with Jinja2; builds a `pages` lookup dict (slug → `title`/`canonical_path`/`page_type`/`description`/`nav_label`/project fields) and passes it into every template render so nav, breadcrumbs, and index pages can resolve real titles/URLs instead of hardcoding them; derives each page's **output path from its `canonical_path`** rather than its source filename (`"/"` → `index.html`, `/about.html` → `about.html`, `/services/epoxy-flooring/` → `services/epoxy-flooring/index.html`, creating directories as needed); writes `sitemap.xml`/`robots.txt`; forces the correct line endings per file (`*.html` is CRLF, `sitemap.xml`/`robots.txt` are bare LF — an existing repo inconsistency this build preserves rather than "fixes"); and, as part of `--check`, runs every rendered page through `build/path_validator.py`. Its one dependency (Jinja2) is pinned in `build/requirements.txt`.
  - `build/path_validator.py` — a small, standalone-importable module that scans a rendered HTML string for any `href`/`src` that isn't root-relative (`/...`), a fragment (`#...`), absolute (`http(s)://...`), or `tel:`/`mailto:`. This is the regression guard for the root-relative convention below: `build.py --check` fails non-zero with a clear message (and the offending paths) the moment any page slips back to a page-relative link.
  - `build/watch.py` — dev-only convenience, not part of the deploy: polls `build/` and reruns `build.py` on every `.jinja`/`.json` change, for use with a live-reload static server during editing.
  - **Never hand-edit any generated `*.html` file, `sitemap.xml`, or `robots.txt` directly** — they are generated output. Edit `build/templates/` or `build/pages/`, run `python build/build.py`, then commit both together. Full create/update/delete recipes: [README.md](README.md).
- **Root-relative paths**: every internal `href`/`src` — nav links, images, `style.css`/`app.js`/`contact-form.js`, cross-page links — is written root-relative (`/assets/...`, `/style.css`, `/about.html`, `/services/epoxy-flooring/`), never relative to the current page. This is required because pages now render at arbitrary nesting depth (e.g. `services/epoxy-flooring/index.html`); a page-relative link there would resolve against `/services/epoxy-flooring/` instead of the repo root. `build/path_validator.py` enforces this on every `--check`.
- **Current page inventory**: home (`/`), About (`/about.html`), two services (`/services/epoxy-flooring/`, `/services/concrete-coating/`), five locations (`/locations/lutz/`, `/tampa/`, `/st-petersburg/`, `/lakeland/`, `/orlando/`) plus a `/locations/` index, one resource article (`/resources/epoxy-vs-polyaspartic/`) plus a `/resources/` index, and a `/projects/` index with one real project (`/projects/hotel-flake-epoxy-st-petersburg/`). The `/locations/`, `/resources/`, and `/projects/` index pages (and the header/footer nav) render their entries by iterating the `pages` lookup dict filtered to the matching `page_type` — adding a new location/resource/project page requires no index-template or nav changes.
- `style.css` holds only the overrides layered on top of Bootstrap 5.3.3 and Bootstrap Icons (both loaded from the jsdelivr CDN in `<head>`, not vendored). Layout is otherwise done with Bootstrap utility classes directly in the markup, not custom CSS.
- `app.js`: sets the footer copyright year, and closes the mobile nav collapse when a real destination link is clicked (any `.nav-link` that isn't a dropdown toggle, or a `.dropdown-item`) or on an outside click — the Services/Locations dropdown *toggles* are deliberately excluded so tapping them opens Bootstrap's dropdown menu instead of collapsing the whole mobile nav first.
- `contact-form.js`: behavior only for the "Request a Free Quote" form — the markup itself is server-rendered by the `contact_form()` macro in `build/templates/_components.jinja` (see above), not injected by this script. No-ops on pages that don't render the form (it looks for `#quoteForm` and returns early if absent). Submits to Web3Forms; reads its access key back from the form's own hidden `access_key` field rather than duplicating it — that field is templated from the `WEB3FORMS_ACCESS_KEY` constant in `build/build.py` (a public Web3Forms site key, meant to be client-visible, not a secret). The form is two-step: step 1 (name/email/phone) is silently POSTed in the background the moment the visitor advances to step 2, so partial leads aren't lost if they abandon before finishing.
- `assets/` holds all images. Photos are stored as JPEG (re-encoded with Pillow, `optimize=True, progressive=True`, quality ~82); PNG is reserved for logo/mascot artwork that needs transparency. `favicon.ico`, `favicon-16x16.png`, `favicon-32x32.png`, and `apple-touch-icon.png` were generated from `assets/hero-standing.png` (the mascot) — regenerate from that source if the mascot art changes rather than hand-editing the icon files. `assets/placeholder-project-photo.jpg` is a generated gray placeholder (also via Pillow) for project pages awaiting real before/after photos — swap it out (and remove the `TODO` comment referencing it) once real photos exist for that project.
- `robots.txt` is generated output (its `Sitemap:` line is built from `SITE_BASE_URL`) — don't hand-edit it; edit `build/build.py`'s `build_robots()` for structural changes. If the domain in `CNAME` ever changes: update `SITE_BASE_URL` in `build/build.py` — this alone drives the canonical/OG/sitemap URLs for every page, the JSON-LD `image`/`url` fields, and `robots.txt`'s `Sitemap:` line — then rerun `python build/build.py` and commit the regenerated output. The JSON-LD `sameAs` field (the LinkedIn company URL) is unrelated to the site's own domain and doesn't need touching.
